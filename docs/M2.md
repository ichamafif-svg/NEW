# M2 — état actuel de la maintenance

La refonte du tour 2, initialement conservée sous `e6ec30e`, est reprise et intégrée. Le sujet n'est plus une PR mutable : c'est une transition de dépôt `base → head`. Cette description porte sur le code actif ; la cible plus complète des cinq contrats est dans [COEUR-STABLE.md](COEUR-STABLE.md).

## Loi de la réparation

`remediate(area,item,base,head)` dérive `repo:{area}:{item}/{base}/{head}`. Les faits permettant cet effet portent sur cette ressource exacte, donc sur ses deux SHA.

| Voie | Faits indépendants requis |
|---|---|
| Autonome | `tests=green` et `reproduced=yes` |
| Revue | `tests=green` et `review=approved`, signé par le reviewer habilité |

Le profil de l'opération vient de la loi. La capacité ne dispense ni de ses conditions, ni des restrictions ou du recontrôle au départ. La seule CI externe verte ou une liste de chemins de dépendances ne suffit plus.

Le scanner vérifie l'applicabilité : main est la base et le head est son enfant direct. Il calcule la recette attendue depuis le checkout et ses données, puis compare chemins et contenu des blobs entre les arbres. **Cette comparaison n'inclut pas encore les modes Git et gitlinks** ; elle ne prouve pas intégralement la transformation de tout l'arbre.

## Recettes et préparation

`ops/recipes.py` définit les recettes de vulnérabilités, SBOM et actions. La recette de vulnérabilités choisit une version à partir des versions de correction des advisories ; elle ne démontre pas la fermeture transitive ni la compatibilité de l'environnement. La recette SBOM décrit les pins lus, sans certification CycloneDX complète. La recette d'actions épingle les lignes reconnues ; une sortie sans changement ne crée pas de proposition.

Une modification nécessitant du jugement est préparée par le modèle et demande une revue signée. `ops/agent.py` limite les chemins de sortie. Le contexte peut encore contenir des secrets : la politique d'egress du contrat cible reste à réaliser. Les recettes reproductibles ne signifient pas que leurs données externes ou leur calcul sont sans faute.

L'agent crée les objets commit par API, déclare le sujet dans le journal puis conserve son accessibilité via `refs/standard/proposals/{head}`. Il n'ouvre plus de PR. Ces créations et la sortie modèle ne passent pas encore par le même contrat physique que `remediate`.

## Instruments et rôles

| Commande | Entrées et résultat | Clés Standard nécessaires |
|---|---|---|
| `init` | Racine, loi client et propositions de grants ; création de la genèse | Quorum humain et témoins dans la démonstration |
| `activate` | Activation après délai attesté | Quorum humain et témoins dans la démonstration |
| `witness` | Checkpoint signé de la tête actuelle | `w1`, `w2` |
| `measure` | Sondes et reproductibilité → `measured.json` | Aucune ; jeton GitHub de lecture |
| `test` | Suite de main sur main et heads déclarés → `tested.json` | Aucune ; checkout/fetch public dans la démonstration |
| `scan` | Signe les résultats de ces fichiers ; réconcilie les effets | Scanner ; jeton de lecture |
| `agent` | Demande les intentions prêtes, retire les propositions mortes, en prépare une | Agent ; App de création de commits et éventuel modèle |
| `guard` | Token, réservation, recontrôle et tentative de fast-forward | Guard ; App d'écriture |
| `review --head SHA` | Revue d'une transition déclarée identifiée par le head | Reviewer ; le CLI demande encore un checkpoint avec les clés témoins |
| `attest` | Observation organisationnelle | Responsable conformité ; même dépendance actuelle aux témoins |
| `report` | Santé, plan, dossier et phases | Aucune clé de signature |

Le runner crée un environnement Python temporaire, installe le lock du sujet et les dépendances de test de la base, puis lance les tests de la base avec une configuration pytest séparée. L'univers vient des cas que la suite de main a exécutés ; un XML fourni par le code exécuté peut être falsifié. Le runner n'est pas un sandbox de code hostile. Son signal est nécessaire et jamais suffisant à l'autonomie.

Le workflow `demo/.github/workflows/standard.yml` sépare les instruments des rôles signataires. Il transporte leurs JSON par artefact et intercale un job de témoins avant scan, agent et guard. Le job instruments ne reçoit ni clés Standard ni credential d'écriture et les checkouts n'y conservent pas de credential Git. Ce câblage n'est pas une preuve de confinement du runner ou d'indépendance physique des personnes.

## Cycle des propositions

Avant intention : mesure → prêt ou attente de revue → retrait si tests non verts, sujet disparu ou délai de revue dépassé (trois jours). Après intention : automate `floor0.LINE`, réservation, résultat, réconciliation et preuve. Un échec de collecte d'un sujet devient `unanswerable` pour ce sujet ; un échec de fabrication est enregistré et soumis à un backoff d'un jour.

Une transition exacte déjà retirée ne peut pas être rouverte automatiquement par la recréation du même commit. Une nouvelle proposition ou une intervention explicite est nécessaire. La cible est libérée dans la vue des sujets vivants ; cela ne prouve pas qu'une réparation différente sera possible.

Après le retrait d'une proposition dont les tests sont rouges, le même passage
agent n'émet pas immédiatement une nouvelle proposition pour cette cible. Le
passage suivant peut réévaluer la cible sous la loi et les mesures courantes.

Les intentions et tokens expirés ne disposent toujours pas d'une reprise complète. Le statut de retrait appartient à la projection ops, pas à un nouvel automate canonique du noyau. La vue de travail générique de `maintenance/` reste séparée ; les sondes M2 connues utilisent les cibles de la loi effective, mais les nouvelles cibles client sans instrument et leurs routes ne sont pas encore couvertes par un moteur commun.

## Adaptateur et résultat

L'adaptateur GitHub lit main puis met à jour sa ref avec `force=false`, vers le head jugé. Une main déjà égale au head donne `ok`; une base différente avant départ donne `failed`; une réponse incertaine donne `unknown`.

GitHub ne reçoit pas ici de compare-and-swap sur la base. L'exclusivité du guard et les protections effectives sont donc des conditions de déploiement, pas des garanties établies par cette paire GET/PATCH. Le probe de protection regarde la présence des types `update`, `deletion`, `non_fast_forward`; il ne vérifie pas leurs bypass ni la configuration complète.

Le scanner considère un head égal à main ou ancêtre de main comme appliqué. Sinon il déclare encore `not_applied` : cela ne prouve pas l'absence définitive d'une demande distante en cours. La preuve d'effet ferme `proof`; seule une mesure satisfaisante de la cible peut fermer son écart.

## Cibles et conformité

Les floors comprennent un inventaire, huit mesures techniques (vulnérabilités, âge, licences, secrets, SAST, tests, actions et SBOM), deux réglages humains (protection de main et lignée), une déclaration d'applicabilité et dix-huit attestations organisationnelles. La lignée examine les commits après l'ancre et constate ceux sans effet jugé appliqué.

Les secrets sont désormais recherchés dans les bytes de tous les chemins suivis, y compris fichiers NUL ; les fichiers trop grands restent non couverts. Les actions sont parcourues dans le YAML chargé, y compris actions locales composites. Bandit ignore les suppressions `nosec`. Le lock reste une liste de pins supposée complète ; la licence est encore obtenue depuis les métadonnées PyPI courantes plutôt que l'artefact exact.

Le dossier projette ces observations sur 93 contrôles ISO 27001, 12 exigences NIS2 et 19 articles DORA. Ses mappings peuvent encore surévaluer la portée d'une attestation générale ; le rejeu ne certifie ni conformité juridique ni contrôle effectif du fournisseur.

## Utilisation de la démonstration

Adopter un SHA immuable via `STANDARD_REF` et une **nouvelle** `STANDARD_GENESIS`. Le workflow refuse une référence non SHA ou une genèse absente. Les environnements `standard-witness`, `standard-scan`, `standard-agent`, `standard-guard` fournissent leurs seules clés et Apps respectives. Les permissions et bypass fournisseur doivent être configurés et examinés par l'opérateur.

L'état voyage encore par `standard-journal` et `standard-pins` dans le dépôt maintenu. Ces branches d'état ne sont pas les anciennes branches de développement supprimées. Leurs pushes séparés après un effet ne constituent pas une durabilité de production ; une réservation locale peut être perdue avec un runner. Ne pas présenter ce workflow comme le service durable décrit par le contrat cible.

L'horodatage ops reste plafonné à l'ancre, le lancement reste `python -m ops`, et le rapport peut encore échouer sur un verdict FAULT incomplet. `report` est désormais programmé même après un échec d'un rôle ; cela ne corrige pas à lui seul sa gestion de FAULT. Ces limites restent des travaux ouverts.
