# M2 — Maintenance autonome, sûre et conforme

Le jalon M2 démontre que des agents maintiennent un vrai dépôt sous la loi, sans pouvoir la contourner, et que le
même journal sert de preuve de conformité ISO 27001, NIS2 et DORA.

## Ce qui est construit

| Élément | Emplacement | Confiance |
|---|---|---|
| Floors sécurité et conformité | `tcb/floors.py` | TCB (sûreté) |
| Op `remediate` liée au commit exact | `tcb/floors.py`, `tcb/law.py` | TCB (sûreté) |
| Adaptateur de fusion GitHub | `adapters/github.py` | TCB (sûreté) |
| Scanner, agent Claude, guard, rapport | `ops/` | hors TCB |
| Catalogue de contrôles et dossier | `compliance/` | hors TCB, projection |
| Service de démonstration et workflow | `demo/` | dépôt maintenu |

Budget de sûreté : 2 465 lignes sur 2 942 (`make check`).

## Les floors

Les floors définissent trois familles de mesures :

- **8 mesures techniques**, observées par le scanner et réparables par `remediate` :
  - vulnérabilités connues ;
  - dépendances en retard d'une version majeure ;
  - licences ;
  - secrets dans le code ;
  - SAST (sévérité haute) ;
  - CI de `main` ;
  - actions épinglées par SHA ;
  - SBOM à jour.
- **1 réglage** que le scanner observe mais qu'aucune PR ne change : `main` exige une PR et des statuts de CI. Son écart va aux humains.
- **18 attestations organisationnelles**, signées par le responsable conformité (un humain) et rattachées à une déclaration d'applicabilité :
  - politique de sécurité, risques, revue des accès ;
  - formation, RH ;
  - registre fournisseurs, incidents, continuité, sauvegarde ;
  - légal, audit indépendant, sites physiques, cryptographie ;
  - tests de résilience, actifs, socle d'infrastructure, supervision, veille sur les menaces.

  Chaque attestation expire selon sa fraîcheur (90 à 365 jours) : l'écart se rouvre seul.

Chaque mesure a une échéance. Une vulnérabilité ouverte depuis 7 jours, ou un secret présent depuis 1 jour, est escaladée aux humains.

## L'autonomie, bornée par la loi

`remediate(area, item, pr, head, method)` a pour ressource `repo:{area}:{item}/pr/{pr}/{head}`. Cette ressource est le commit exact, rangé sous la cible qu'il répare. Les faits qui autorisent la fusion sont observés sur cette ressource même, donc sur ce commit.

- **Fusion autonome** : le scanner a observé ce commit avec la CI verte (`ci = green`) et un périmètre limité aux dépendances (`scope = dependencies`).
- **Fusion après revue** : la CI est verte et une revue `approved` a été observée sur ce commit, par un compte autre que l'agent.
- **Un autre commit** n'est jamais couvert par ces faits.
- **L'agent ne peut pas observer son propre commit.** Ses chaînes de capacités ne sont pas indépendantes de son intention.
- **Le guard envoie `sha = head`** à GitHub. Si la branche a bougé, GitHub refuse : rien n'est fusionné, l'issue est `failed`.

Après fusion, le scanner relit la PR. Si elle est fusionnée à ce SHA, il signe la preuve qui ferme l'obligation de l'effet. La cible n'est prouvée que par une nouvelle mesure de `main`.

## Rôles et clés

| Job | Environnement GitHub | Identités | Jetons |
|---|---|---|---|
| `scan` | `standard-scan` | `scanner`, `w1`, `w2` | `GITHUB_TOKEN` (écrit l'état, lit PR et CI) |
| `ask` | `standard-agent` | `agent` | `GITHUB_TOKEN` (écrit l'état) |
| `guard` | `standard-guard` | `guard` | App guard, seule autorisée à mettre à jour `main` |
| `report` | — | aucune | `GITHUB_TOKEN` (écrit l'état) |
| `repair` | `standard-agent` | aucune clé | App agent (branches et PR, sans contournement), clé API Claude |

Les secrets d'un rôle vivent dans un environnement que seule `main` peut utiliser. Aucune pull request, même de l'agent, ne peut donc les lire.

Le pin de genèse est une variable d'administration (`STANDARD_GENESIS`). Un journal remplacé sur sa branche est refusé avant toute lecture.

Les quatre clés humaines ne sont jamais dans la CI. FLOOR-0 exige un quorum de 2 humains, plus 2 pour sortir d'un veto. Elles servent à :
- la genèse ;
- les capacités ;
- les attestations.

## Dossier de conformité

`python -m compliance build` rejoue le journal avec `tcb.audit` et projette les mesures sur :
- les 93 contrôles de l'Annexe A d'ISO 27001:2022 ;
- 12 exigences NIS2 (articles 20, 21(2) a–j, 23) ;
- 19 articles DORA (gouvernance, gestion du risque TIC, incidents, tests de résilience, prestataires tiers).

Pour chaque contrôle, le dossier indique :
- les mesures qui le prouvent, avec l'entrée signée, l'auteur et la date ;
- les écarts restants, avec leur échéance.

`python -m compliance verify` reconstruit le dossier depuis le journal et exige une égalité octet pour octet. La mesure `journal` (séparation des tâches, gestion des changements, recueil de preuves, droits privilégiés) est prouvée par le rejeu lui-même.

## Revue adversariale indépendante

Une revue par un agent qui n'avait pas écrit le code a trouvé 12 points, dont 4 graves. Tous sont corrigés et couverts par `tests/test_m2_review.py`.

| # | Constat | Correction |
|---|---|---|
| V1 | Une PR de fork nommée comme celles de l'agent empruntait son autonomie ; un compte sans droit pouvait « approuver » ; la base n'était pas vérifiée | Seules les PR de l'App agent, depuis ce dépôt et vers `main`, sont observées. Une revue compte si elle vient d'un compte en écriture, porte sur ce commit et qu'aucune objection n'est en cours |
| V2 | Un jeton capable d'écrire l'état pouvait substituer une genèse entière | Le pin de genèse est externe (variable d'administration, `--genesis` du vérificateur). Permissions par job, état protégé par règle de branche |
| V3 | Une réponse du modèle pouvait écrire `.git/config` | Liste blanche de chemins résolus. Git est durci (fsmonitor, hooks). Le job `repair` n'a plus aucune clé Standard |
| V4 | L'audit installait les dépendances, donc exécutait du code tiers, à côté des clés du scanner | `pip-audit --no-deps --disable-pip` sur un verrou complet : rien n'est installé. Outils épinglés |
| V5–V6 | Un audit en échec ou un fichier au nom contenant un espace donnaient « none » | Échec ou dépendance non auditée : `error`. `git ls-files -z`. Fichier trop gros : `error` |
| V7 | Une CI de fork sur une branche nommée `main` passait pour celle de `main` | Seul le run `push` de ce dépôt, au SHA courant de `main`, compte |
| V8, V10 | Listes de fichiers ou de PR tronquées à 100 | Pagination. Liste incomplète : périmètre `code` |
| V9 | Une fusion refusée ou incertaine bloquait la cible pour toujours | Incertaine : le scanner réconcilie en relisant la PR. Refusée : nouvelle intention `retry_of` après une observation plus récente du commit |
| V11 | Le vérificateur acceptait n'importe quelle date | Il affiche la date pour laquelle le dossier parle |
| V12 | Une op `{x}/noop` « réparait » n'importe quelle cible | La route enfant doit contenir un paramètre typé. Un gel doit viser `repo:deps:vulns/*` pour couvrir les PR |

La seconde passe de la même revue a fermé ces corrections. Elle a ensuite trouvé six points, eux aussi corrigés et testés :

- **Garde mort après sa réservation** : la ligne passe `expired` et le scanner la réconcilie par relecture.
- **Inondation de PR** : les PR de l'agent sont cherchées par auteur ; aucun débordement ne les masque.
- **Blocage de `repair`** : il ne voit que les PR de l'agent, si bien qu'une PR de fork nommée `standard/...` ne le bloque plus.
- **Objection d'un inconnu** : seules les revues des comptes en écriture comptent, objections comprises.
- **Lien symbolique vers `.git`** : chaque composant du chemin est vérifié avant résolution.
- **PR reciblée** : l'adaptateur refuse une PR dont la base n'est pas `main`.

Les binaires ne bloquent plus l'analyse des secrets.

Points qui tiennent :
- **Commit exact** : les faits d'un commit n'en couvrent jamais un autre.
- **Pas d'auto-observation** : l'agent ne peut pas observer son propre commit.
- **Pas de double fusion** : la relecture se fait avant l'envoi.
- **SHA vérifié par GitHub** : `sha` empêche toute fusion d'un autre commit.
- **Aucune autorité** : la règle de route n'accorde aucun droit.

## Limites assumées de la démonstration

- **Clés humaines** : les quatre sont générées pour la démo. En production, elles appartiennent à quatre personnes distinctes, idéalement sur passkeys (WebAuthn est déjà supporté par la TCB).
- **Témoins** : `w1` et `w2` tournent dans le même job que le scanner. En production, ce sont deux domaines indépendants.
- **Attestations** : un même humain (`second`) atteste les 18 mesures organisationnelles, sans empreinte du document attesté. En production, chaque responsable atteste sa mesure et l'empreinte du document entre dans la preuve.
- **Épingles** : elles vivent sur une autre branche du même dépôt. En production, c'est un domaine de restauration séparé.
- **Revue humaine** : elle est attestée par le scanner, qui lit l'API GitHub, et non signée par la clé du relecteur.
- **Couverture d'écosystème** : le scanner couvre Python (pip-audit, bandit). Les autres écosystèmes sont des sondes à ajouter, pas des changements de loi.
- **Conformité** : un statut PROUVÉ est une preuve technique ou une attestation signée, pas une certification. Les contrôles organisationnels restent du travail humain que le système rend visible, daté et prouvable.
